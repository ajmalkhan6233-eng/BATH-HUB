# ROYAL BATH HUB: ARCHITECTURE BRIEF FOR THE UI/UX UPGRADE (23 Oct 2026)
Facts read from the code on branch `work` + `claude/owner-ui-fixes` (not guesses). Items I could not prove are marked UNVERIFIED.
Shop: Royal Bath Hub, Kandy Road, Thihariya, Sri Lanka. Owner "AJ" works mostly on an iPhone and a Windows PC, voice-to-text, wants few clicks. Halal business rules (no interest, honest pricing).
Two AIs: Claude (chat) writes all code and pushes a branch; Claude Code on AJ's PC only pulls, tests, merges, restarts. Gemini = design/structure proposals; Claude builds them.

## CORE ARCHITECTURE
1. **Frontend:** NO framework. Plain HTML + vanilla JS + CSS in `public/` (42 .html pages, 22 .js files, ~14,500 lines of HTML). Libraries are only local files (xlsx, pdf.js). The owner shell is `public/bathco_complete.html` (2,772 lines, served at `/owner`). The public website is a SEPARATE repo (React + Vite + Tailwind on Netlify) and is not part of this brief.
2. **Backend:** Node.js + Express (`server.js`, 3,460 lines) mounting 58 route modules in `routes/` (plus `middleware/` x4, `utils/` x71). Sessions: express-session stored in Postgres (connect-pg-simple), bcrypt logins, optional TOTP, roles admin/owner/staff, helmet, rate limits. Some routes are factory functions (`createVendorLedgerRouter({pool, requireAuth})`), some are inline in server.js.
3. **Database:** PostgreSQL via `pg`, ONE shared pool (`utils/pool.js`). NO ORM. Hand-written parameterised SQL inside route files. Tables are created by `CREATE TABLE IF NOT EXISTS` when each route module loads, plus a few additive scripts (`scripts/migrate_*.js`). Money is NUMERIC; node-postgres returns it as text, so routes convert with Number()/round2.
4. **Hosting:** AJ's Windows PC, run by pm2 as `apex-server` on port 3100 (a watchdog task restarts it; health check `/health`). Public website on Netlify. No Docker, no cloud app host for the shop app. Phone access to the PC app: UNVERIFIED (depends on his network/tunnel).
5. **PWA:** Yes. `public/manifest.json` + `public/service-worker.js` (cache version v26). Static files precached. API GET = network-first, falling back to the last good answer (header `X-Saved-Copy: 1`). API writes are never cached.

## ROUTING & STATE
6. **Navigation:** hybrid. The shell is a single-page app: sidebar + topbar stay, `navigate(page)` shows/hides `.page` divs, address-bar routes `#/page`. Many screens are separate HTML files opened inside the shell as iframes (7 frames: POS, Prices, Stickers, Vendors overview, Customers, Credit, Quotations...; added with `addFramePage({key,label,icon,url,sub,after})`). So: shell = SPA, each inside-screen = its own multi-page document with its own JS.
7. **Global state:** none. No store. Each screen does its own `fetch('/api/...')` and keeps data in local variables. Small prefs in `localStorage` (theme, Simple/Full menu, hidden menu items, group open/closed).
8. **Caching:** no in-page data cache; every click is a fresh fetch. Only the service worker's last-good-copy for offline. Dashboard auto-refreshes every 60 s.
9. **State preservation:** partial. Writes use an offline queue (`public/offline-queue.js`, IndexedDB; retries; shows ONLINE / OFFLINE / SYNCING / SYNC ERROR pill) and `public/lib/offlineSave.js` with an Idempotency-Key per save (`middleware/idempotency.js`) so retries never double-save. `daily-entry-v2.html` autosaves on `beforeunload`. Most other forms have NO draft: an accidental refresh loses typed-but-unsaved data. (Refresh button now reloads data only, not the page.)

## VENDOR MODULE (two parallel systems today)
10. **Schema A, the vendor ledger** (`scripts/migrate_vendor_ledger.js`, additive): `vendor_bills`(id, branch_id, vendor_name TEXT, bill_no, bill_date, due_date, total>0, grn_id INT nullable, photo_path, notes, voided, created_by) -> children by `bill_id`: `vendor_bill_cheques`(cheque_no, bank, payee, amount, cheque_date, due_date, same_bank, status ISSUED|CLEARED|BOUNCED|CANCELLED), `vendor_payments`(amount, method, paid_at, note), `vendor_credit_notes`(note_no, amount, note_date, reason). **Schema B, purchasing:** `suppliers`(id, name, phone, category, notes, active), `supplier_payments`(supplier_id, amount, pay_date, method), `grn_records`(grn_number, supplier_id, supplier_name TEXT, grn_date, item lines, total_amount), `pur_purchase_orders`(po_number, supplier_id, ...), `pur_supplier_prices`, `pur_shipments`. HEADS-UP: there is no single vendors master table. Schema A identifies a vendor by NAME text; Schema B by `suppliers.id`. They are not foreign-keyed together.
11. **Vendor page data:** separate calls. `GET /api/vendor-ledger/summary` (per-vendor outstanding, covered, uncovered, cleared), `GET /api/vendor-ledger/bills?vendor=&state=` (bills + status + cheques), plus `/calendar`, `/cash-gap`, `/checks`, `/audit-log`, `/export.csv`; writes `POST /bills`, `/bills/:id/cheques|payments|credit-notes|void`, `/cheques/:id/clear|bounce|cancel`. `GET /api/vendor-credit/summary` and `/vendor` are a separate "credit price" module. Server side: `loadRows()` reads all bills then 3 child queries with `IN (...)` (no N+1), then JS maths in `utils/vendorLedger.js` (`billStatus`, `summarise`). `public/vendors_overview.html` calls `/bills` and totals per vendor in the browser. Not one aggregated SQL query.
12. **Running ledger:** NO. There is no Debit / Credit / Running Balance statement. Only per-bill status (outstanding = total - payments - credit notes, cheques counted as "covered" until cleared) and per-vendor totals. A per-vendor statement does not exist yet.
13. **Links:** GRN -> bill by nullable `vendor_bills.grn_id` (no FK); payments/cheques/credit notes -> bill by `bill_id` (FK). PO <-> GRN matching by `GET /api/po-grn-matches` (computed). Schema B owed = GRN totals minus `supplier_payments` (`GET /api/supplier-aging`). So the two systems can disagree.

## UI / UX
14. **Layout:** shared persistent layout exists only in the shell: sidebar (grouped: Daily work, Items, Purchasing, Money, Reports, Papers, Customers and web, Settings and admin; Simple vs Full menu; per-device "Customize menu"), topbar (title, status pill, clock, theme, refresh, sign out), content area. Inside iframes each page has its own header/styles. Design tokens in `bathhub-design.css` + `design2_tokens.css`; themes Gold(default, ash/black/gold), Water, Light.
15. **Data entry:** mostly in-page forms and inline panels; native `prompt()` / `confirm()` for small things (e.g. "Why?" on bounce). A few custom overlays (Customize menu, Command-centre breakdown drawer). No shared modal/drawer component. New URL/page for each big job (GRN, vendor ledger, purchasing).
16. **Keyboard:** minimal. POS item search: Up/Down/Enter/Esc; POS scan box and find box: Enter; login: Enter; breakdown panel: Esc. NO global shortcuts (no Ctrl+K search, no hotkeys to open POS/new bill/pay).
17. **Tables:** plain HTML `<table>`; server SQL uses LIMIT (about 100-300). No pagination UI, no virtual scrolling, no column resize. The Prices table lists all ~135 items. New Command-centre panels add search, sort, total, CSV download.

## REFACTOR PATHWAY
18. **Modularity:** good at the file level (one route file per feature, utils per concern, tests in `tests/`, 24 test files, jest). Weak spots: `server.js` still holds many inline routes; large single-file pages (`daily-entry-v2.html` 4,638 lines; `bathco_complete.html` 2,772 lines); each route creates its own tables at load. "Golden core" files (AGENT_GUIDE/09_golden_core.md) must never be edited.
19. **Build tool:** none. No bundler, no transpile. Edit a file, restart pm2 (or just reload for static files; service worker version bump needed to bust cache). New UI = new .html/.js file + one `<script>` tag or one `addFramePage(...)` line. Cheapest path for Gemini designs: vanilla JS + CSS variables from `bathhub-design.css`; no React/Tailwind.
20. **Recommended way to add "Vendor 360" + persistent navigation without breaking anything:**
   - New files only: `routes/vendor360.js` (READ-ONLY, owner only, mounted with one line in server.js), `public/vendor360.html` + `public/vendor360.js`, `tests/vendor360.test.js`. Register it with ONE `addFramePage({key:'vendor360', ...})` line; keep all old pages and URLs working.
   - New endpoints: `GET /api/vendor360/list` (one aggregated SQL: bills, paid, credit notes, cheques pending, outstanding, last bill date per vendor), `GET /api/vendor360/:vendor` (profile + totals), `GET /api/vendor360/:vendor/statement` (UNION of bills = Debit and payments / cleared cheques / credit notes = Credit, ordered by date, running balance with `SUM() OVER (ORDER BY date,id)`).
   - Tabs: Overview, Bills, Payments, Cheques, Credit notes, Statement (running balance), GRNs, Documents. Left = vendor list with search; deep link `#/vendor360/<name>`.
   - Fix the root cause later in its own task: add `vendor_id` to vendor_bills (additive migration, backfill from names), never drop or rename tables.
   - Add a small global command palette (Ctrl+K) as its own module `public/lib/palette.js` loaded by the shell: jump to a screen, find an item by code, find a vendor, start a new bill.
   - Side drawer for "Add bill / Add payment" instead of a new page; keep Esc to close; draft saved to localStorage so a refresh does not lose typing.
